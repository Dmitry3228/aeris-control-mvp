# Demo and QA guide

## Presenter flow

Start with `docker compose up --build -d`, then confirm all six rows in `docker compose ps` are healthy. Open <http://localhost:3100> at desktop width.

1. **Overview:** call out the 12 live fleet rows, status metrics, one-hour pressure trend, and responsive operational shell.
2. **Live alarm:** show the highlighted `AHU-204` high-pressure row and **High discharge pressure** alarm generated by real simulator telemetry.
3. **Acknowledge:** select **Acknowledge** and show that the unresolved alarm remains in the operational summary with a distinct lifecycle badge until recovery closes it.
4. **Equipment detail:** open `AHU-204` and show its live pressure, temperature, power, zone, truthful operational state, and historical pressure chart beside command history.
5. **Command round trip:** send a `22.5 °C` setpoint. The API persists `PENDING`, publishes MQTT, the simulator responds, and the UI polls to **Acknowledged**.

No login or external credential is required.

## Visual fidelity review

The final QA pass opened both approved concepts and both final real-app overview captures together at original resolution. Concrete findings:

1. The desktop implementation preserves the concept's left navigation rail, top plant/status bar, dense two-column operations grid, and cyan active-navigation treatment.
2. The title block and three semantic metric cards retain the concept hierarchy and green/orange/cyan color language; real values show 12 online, one active alarm, and an honest unavailable energy value.
3. The real fleet contains the same 12 `AHU-201`–`AHU-212` rows and zones, with `AHU-204` selected in cyan and its high-pressure state called out in orange.
4. The real alarm card keeps the danger rail/icon, timestamp, primary acknowledge action, secondary view action, and switches above the fleet at mobile width.
5. The overview and detail pressure panels retain the `1H/6H/24H/7D` control, shared chart scale, orange 7.5 bar threshold, cyan live series/marker, and current/min/max summary; a fresh installation seeds 12 unique points over the prior hour, while ordinary restarts reuse persisted history without duplicating it.
6. The mobile capture preserves the compact brand/health header, three-up metrics, readable four-column fleet treatment, 44 px actions, and fixed three-item bottom navigation without horizontal clipping.
7. Typography, border density, dark navy surfaces, subdued secondary copy, and status-dot vocabulary are consistent across the concepts and implementation.

Copy/data differences are intentional: the concepts contain three illustrative alarms and a fabricated energy total, while the production screenshot shows the one alarm created by real telemetry and `—` for an energy metric that the domain does not calculate. The alarm message includes the actual pressure and threshold inline; the API has no separate measurement field, so the secondary measurement line remains unavailable. Command activity contains only real commands and omits the concept's fictional operator history.

The real E2E recorded zero browser console warnings or errors and zero failed network requests after WebSocket support was added. Automated checks found no horizontal document overflow at either target viewport. The only presentation deviation is that the required 390 × 844 artifact is a true viewport capture (not the concept's tall stitched device mockup), so content below the fold is intentionally excluded. The concept PNGs are QA references only and are not bundled into the product UI.

The in-app browser runtime was attempted first but returned `No browser is available`, and its browser inventory was empty. The accepted Playwright Chromium test runner was therefore used for the full interactive inspection and artifacts.
